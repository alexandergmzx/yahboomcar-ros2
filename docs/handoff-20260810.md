## Addendum 3 — the missing map, and a correction to how I verify RViz

You reported "still no map on rviz for the simulation" on a `--fun` session, with the
scan and robot rendering and only the map absent.

**It was my decision, not a bug.** `e085a8c` forced SLAM off whenever `--fun` was set,
so there was no `/map` to draw. Reverted in **`b28e96c`**: `--fun` runs SLAM again,
`--no-slam` stays for pure driving, and the banner now states the honest caveats (the
map builds as you drive; on isaac it will smear on turns from the open ~3× encoder-yaw
finding; a fun map is never evidence). Verified: 2D fun session reports "map publishing:
5 updates, 4.04 m across" and the map is measurably on screen.

**The more important half is why nothing caught it.** I "verified" those RViz configs by
checking rviz2 stayed alive with zero error lines — which proves nothing, because RViz
renders an empty world just as quietly as a full one. You found it by looking at the
screen. So **`c6228cb`** adds `tools/check_rviz_render.py`: it captures RViz's 3D panel
and counts pixels per display, exiting nonzero naming whichever is absent.

Building it turned up **four ways it could have passed a broken session**, each found by
running the negative control rather than reasoning about it:

1. a fixed 22% left crop left RViz's white Displays panel in frame — white scores as map
   free space;
2. cropping only the left edge still counted the menu bar (67,796 px) and status bar
   (31,187 px): **112,575 px of "map" in a session with no map**;
3. cropping to where the background colour appears was self-defeating — the more the map
   filled the view, the smaller the detected viewport became, until the map cropped
   itself away and scored 0 px;
4. with RViz not running at all, capturing the root window photographed the desktop and
   passed everything (426,101 px of "robot" from window chrome).

Fixed by capturing RViz's 3D panel as its own X window, so the frame *is* the viewport
and nothing depends on content, plus a hard failure when no RViz window exists.

**Measured both directions** (2D fun, domain 67): SLAM on → map 46,408 px, PASS.
`--no-slam` → map 812 px, **FAIL naming `map`** while scan (10,208) and robot (1,203)
still pass. Threshold 2000 sits 2.5× above the noise floor and 23× below the signal.
Isaac fun session: map 46,230 px, PASS — captures in the session scratchpad.

Scope of the new tool, stated plainly: it proves a display is **on the screen**. It says
nothing about whether the map is *correct* — that is `score_slam_map.py`, against tape
measurements. `docs/slam-delivery-plan.md` records both that boundary and that a
`--fun` map is never a delivery artifact.

Close-out: sims down, isaac lock released after verifying the process died, 8 stale DDS
segments cleared with the parallel session's 9 live ones untouched, 209 tests green,
**nothing pushed**.
